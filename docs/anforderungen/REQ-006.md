## Beschreibung

Heute sieht man die Messwerte nur als Text im Seriellen Monitor. Neu gibt es ein GUI im Browser (`tools/gui/jointsense_live.html`), das beide IMUs als Graphen zeigt und die Überstreckung grün/rot anzeigt. Dafür schickt die Firmware im **GUI-Modus** keine Texte mehr, sondern nur kurze, maschinenlesbare Zeilen mit 115200 Baud. Ein Schalter oben in `jointsense.ino` wählt den Modus. Ist er aus, verhält sich das Gerät genau wie heute.

Das Messen, Warnen und Einmessen selbst ändert sich **nicht**. Es geht nur um die Ausgabe.

**Team-Entscheid (2026-11-13):** Für diese REQ gibt es **keinen Tester-Durchgang**, weil sie nur die Anzeige betrifft. Der Developer kompiliert beide Modi und trägt Flash/RAM ein. Geprüft wird am echten Board durch das Team.

## Teil A: Firmware (`jointsense/`, macht der Developer)

### Schalter

- Oben in `jointsense.ino` bei den Einstellungen: `#define GUI_MODUS 1` (1 = GUI, 0 = Text wie heute).
- Alle Text-Meldungen werden mit `#if GUI_MODUS ... #else ... #endif` wegkompiliert, damit Flash frei wird. Kein `if` zur Laufzeit.

### Protokoll (nur bei `GUI_MODUS 1`)

Regeln für alle Zeilen: eine Zeile = ein Datensatz, Felder mit Komma getrennt, Zeilenende `\n` (`Serial.println` mit `\r\n` ist auch erlaubt), **nur ganze Zahlen**, keine Kommazahlen, keine Leerzeichen. Fehlt ein Wert: Feld leer lassen (zwei Kommas hintereinander).

| Zeile | Wann | Aufbau |
|---|---|---|
| **G** Grenzwert | einmal am Ende von `setup()` | `G,<grenzwert_zehntel>,<hysterese_zehntel>` z. B. `G,50,20` |
| **E** Ereignis | wenn es passiert | `E,<CODE>` (Liste unten) |
| **D** Daten | jeder Messzyklus (alle 20 ms = 50 Hz) | siehe unten |
| **P** Einmess-Fortschritt | 1× pro Sekunde in Schritt 1 und Schritt 2 | `P,<ruhig_zehntelsek>,<beugung>,<oberarm>,<hand>,<achse_prozent>` |
| **Z** Zykluszeit | 1× pro Sekunde (ersetzt «Zyklus max: … us») | `Z,<zyklus_max_us>` |

**D-Zeile:**

`D,<millis>,<ax1>,<ay1>,<az1>,<gx1>,<gy1>,<gz1>,<ax2>,<ay2>,<az2>,<gx2>,<gy2>,<gz2>,<abw_zehntel>,<status>,<schritt>`

- `millis`: Wert von `millis()` in diesem Zyklus.
- `ax1 … gz2`: **Rohwerte** (int16) genau so, wie sie aus der IMU gelesen wurden (GUI rechnet: Beschleunigung / 16384 = g, Gyro / 65,5 = °/s). Hat eine IMU in diesem Zyklus nicht geantwortet: ihre 6 Felder leer.
- `abw_zehntel`: Abweichung von der Referenz in Zehntelgrad, gerundet (z. B. `-123` = −12,3°). **Nur gefüllt**, wenn Referenz gültig, Lage bekannt, beide Messungen gut, kein Ausfall und kein Einmessen. Sonst leer. Begrenzt auf −1800 … +1800.
- `status`: Zahl aus Bits (Bit gesetzt = trifft zu):

  | Bit | Wert | Bedeutung |
  |---|---|---|
  | 0 | 1 | IMU 1 ausgefallen (REQ-001, 3× in Folge) |
  | 1 | 2 | IMU 2 ausgefallen |
  | 2 | 4 | Referenz gültig |
  | 3 | 8 | Lage bekannt |
  | 4 | 16 | zu weit (Überstreckungs-Warnung aktiv, Ergebnis von `grenzwertPruefen`) |
  | 5 | 32 | Motor an (wirklicher Zustand am Pin, auch Stoss und Fehlermuster) |
  | 6 | 64 | Gyro übersteuert (eine der beiden IMUs) |

- `schritt`: Wert von `einmessSchritt` (0 aus, 1 still, 2 warten, 3 frei).

**P-Zeile:** Zahlen aus `einmessenFortschritt`, ganz und abgerundet wie heute (`wertMelden`). `ruhig_zehntelsek` z. B. `14` = 1,4 s. In Schritt 1 sind Beugung/Oberarm/Hand/Achse `0`.

**E-Codes** (das GUI kennt die Texte dazu):

| Code | Ersetzt heute |
|---|---|
| `START` | Beginn von `setup()` |
| `IMU1_OK`, `IMU1_FEHLER`, `IMU2_OK`, `IMU2_FEHLER` | «IMU 1 (Oberarm): OK / FEHLER …» beim Start |
| `AUSFALL` | «FEHLER: … ausgefallen» (nur einmal beim Beginn des Ausfalls; welche IMU, steht in den Status-Bits) |
| `IMU_WIEDER_DA` | «IMUs wieder da.» |
| `SCHRITT1_START` | «Schritt 1: Arm haengen lassen …» |
| `SCHRITT1_FERTIG` | «Schritt 1 fertig. Enter oder Taste …» |
| `SCHRITT2_START` | «Schritt 2: Arm frei bewegen …» |
| `REF_GESETZT` | «Referenz gesetzt.» |
| `EINMESS_ABBRUCH_RUHIG`, `_BESTAETIGUNG`, `_BEUGUNG`, `_OBERARM`, `_HAND`, `_IMU` | «Einmessen abgebrochen - Grund: …» |

Wegfallen im GUI-Modus ohne Ersatz-Zeile (das GUI sieht es aus den D-Zeilen): «Keine Referenz …», «Neigung Oberarm …», «Abweichung: …», wiederholtes «FEHLER» jede Sekunde, die Start-Hilfetexte.

### Akzeptanzkriterien Firmware

- [ ] AK-1: `GUI_MODUS 0`: Ausgabe und Verhalten genau wie vor REQ-006 (9600 Baud, gleiche Texte).
- [ ] AK-2: `GUI_MODUS 1`: Serial läuft mit 115200 Baud, und es erscheint **nur** Zeilen, die mit `G,`, `E,`, `D,`, `P,` oder `Z,` beginnen.
- [ ] AK-3: Im GUI-Modus kommt pro Messzyklus genau eine D-Zeile, im Mittel 50 ± 2 pro Sekunde (am Board gemessen mit dem GUI, Chip «Datenrate»).
- [ ] AK-4: «Zyklus max» (Z-Zeile, gleiche Messung wie heute: Lesen + Rechnen) bleibt im GUI-Modus < 15 ms (REQ-002 AK-15).
- [ ] AK-5: Die Bestätigung über Serial (`' '`, `'\n'`, `'\r'`) und über die Taste funktioniert in beiden Modi wie heute (REQ-004/REQ-005).
- [ ] AK-6: Beide Modi kompilieren für `arduino:avr:uno` ohne Fehler. Flash ≤ 32256 Byte, RAM (globale Variablen) ≤ 70 % = 1434 Byte. Beide Zahlenpaare stehen in `docs/tech-stack.md`.
- [ ] AK-7: Messen, Warnen, Motor und Einmessen verhalten sich in beiden Modi gleich (keine Änderung an `logik.h`/`logik.cpp` nötig).

**Rechnung 50 Hz (Engineer):** Längste D-Zeile ca. 110 Zeichen. Bei 115200 Baud gehen rund 11,5 Zeichen pro ms raus, also ca. 9,5 ms pro Zeile. Ein Zyklus dauert 20 ms, die Leitung ist damit zu etwa 50 % belegt: **50 Hz reicht.** Der Sendepuffer hat 64 Byte, darum wartet `Serial.print` bei einer langen Zeile ca. 4 ms. Das passiert **nach** der Zykluszeit-Messung und bremst die 20-ms-Takte nicht. Falls am Board trotzdem AK-3 oder AK-4 verletzt ist: nur jede 2. D-Zeile senden (25 Hz, reicht für QA-01) und dem Team melden.

## Teil B: GUI (`tools/gui/`, kein Firmware-Code)

Eine einzige Datei `tools/gui/jointsense_live.html`, Doppelklick öffnet sie in Chrome oder Edge. Web Serial API, 115200 Baud. Keine Installation, keine CDN-Links (läuft offline), Graphen selbst mit `<canvas>`. Code simpel und auf Deutsch kommentiert. Vorlage für Farben und Layout: Mockup «Live-Monitor» des Teams (dunkles Dashboard).

- Beim Öffnen automatisch mit dem zuletzt erlaubten Port verbinden (`navigator.serial.getPorts()`), sonst Knopf «Verbinden». Bei Trennung automatisch neu verbinden. Hinweis im GUI: der Uno startet beim Verbinden neu.
- **Kopfzeile:** Verbindungsstatus (Port, Baud), Verbinden/Trennen, Anhalten/Fortsetzen (Graphen einfrieren), Aufnahme als CSV (Download).
- **Statuskarte:** OK = grün, ÜBERSTRECKT = rot, EINMESSEN = blau, SENSORFEHLER = orange. Abweichung gross in Grad, Grenzwert, Abstand, Motor an/aus. Die Farbe kommt **nur aus den Status-Bits und dem Schritt** der Firmware, das GUI rechnet keinen Grenzwert selbst.
- **Graph Abweichung** (10 s, −75° bis +15°): rote Zone über dem Grenzwert, Hysterese gestrichelt, Teile über dem Grenzwert rot. Chips: IMU 1, IMU 2, Referenz, Datenrate (gemessen, Hz), Zyklus max (aus Z-Zeile).
- **Vier Graphen** (10 s): IMU 1/2 Beschleunigung und Gyro, je x/y/z in Blau/Orange/Violett (kein Rot/Grün), mit Live-Zahlen. Leere Felder = Lücke im Graphen und Hinweis «Keine Daten».
- **Einmessen:** Schritt 1 (Ruhig x.x/2.0 s), Schritt 2 mit Balken Beugung /30°, Oberarm /15°, Hand /45°, Achse /100 %. Knopf «Einmessen / Bestätigen» schickt `\n`.
- **Ereignisliste** (ersetzt den Seriellen Monitor), neueste oben, mit Uhrzeit.
- **Demo-Modus** (Checkbox) mit simulierten Zeilen im gleichen Protokoll, damit man das GUI ohne Board ausprobieren kann.
- Unbekannte oder kaputte Zeilen werden still verworfen (kein Absturz des GUI).
- Anleitung `tools/gui/README.md`: Chrome/Edge nötig (Safari/Firefox gehen nicht), Serieller Monitor der Arduino IDE muss zu sein (sonst ist der Port belegt), Schalter `GUI_MODUS` erklären.
